SYSTEM BLUEPRINT

Part 1 — Executive Overview & System Architecture

1.1 Project Mission & Problem Statement

CampusHub LMS is a custom, full-stack Learning Management System engineered from the ground up to streamline modern academic workflows for both students and faculty instructors. Traditional educational portals often suffer from fragmented user interfaces, cumbersome grading mechanics, clunky file storage, and unreliable submission lifecycles. CampusHub solves these problems through:

  • Unified Academic Workspaces: Distinct, role-based dashboards tailored specifically for students and teachers with zero cross-role leakage.
  • Course Administration & Enrollment: Direct student course catalogs, enrollment state tracking, syllabus inspection, and real-time course announcements.
  • Assessment Engine: Timed multiple-choice quizzes with server-side duration enforcement, automated instant scoring, anti-concurrency guards, and transparent student performance rubrics.
  • Assignment Lifecycles: Deadline-aware student assignment submissions and a dedicated teacher evaluation portal with scoring and customized feedback.
  • Secure Cloud Object Storage: A private personal file and folder repository integrated directly with Cloudflare R2, using time-limited presigned URLs (60-second TTL) for authenticated, zero-leak downloads.

1.2 Core Architectural Principles

1. Decoupled Client-Server Boundary

A Single Page Application (SPA) frontend communicating strictly over HTTPS with an asynchronous RESTful JSON API backend. Neither layer makes assumptions about the host environment of the other.

2. Stateless JWT Authentication

No server-side session memory or sticky sessions. All authentication state is carried in cryptographic JSON Web Tokens signed with HMAC-SHA256, enabling effortless horizontal scaling on serverless and containerized cloud platforms.

3. Type-Safe ORM Data Access

Complete elimination of raw, error-prone SQL string concatenation through Prisma ORM 6, enforcing compile-time model consistency, explicit foreign key relationships, and deterministic schema migrations.

4. Resilient Blob Storage Offloading

Large binary files (PDFs, ZIPs, images) are never stored in the database or server filesystem; they are streamed directly to Cloudflare R2 (S3-compatible) with metadata tracking in PostgreSQL and compensation rollbacks on failure.

1.3 Verified System Architecture & Data Pipeline

The application runs across four managed cloud services, completely separating concerns:

  • Client (Frontend): React 19 SPA bundled by Vite 8 and styled with Tailwind CSS v4, deployed globally across Vercel's Edge CDN (campus-hub-delta-sooty.vercel.app).
  • Server (Backend API): Node.js 26 and Express 5 web service hosted on Render, handling routing, middleware authentication, business validation, and database operations.
  • Relational Database: PostgreSQL managed by Neon Serverless Cloud (AWS us-east-2 region), connected via Prisma ORM 6.19.3.
  • Object Storage: Cloudflare R2 private storage bucket, accessed via @aws-sdk/client-s3 and @aws-sdk/s3-request-presigner using S3-compatible endpoints.
Architectural Note on Mongoose in package.json

Inspection of Server/package.json reveals "mongoose": "^9.11.2" listed as a dependency. However, a full codebase static analysis confirms that Mongoose is neither imported nor used anywhere in Server/src. PostgreSQL via Prisma ORM is the sole and authoritative database. The Mongoose dependency is legacy baggage from early prototype scaffolding and can be safely uninstalled.

2.2 Deep Dive: Why Architectural Layers are Separated

1. Why Routes and Controllers are Separated

In Express, a Route is strictly a traffic dispatcher. It defines the HTTP verb, the path pattern, the middleware stack, and points to a controller function. A Controller contains the actual business execution logic.

Why this matters: If an endpoint path changes from /api/course to /api/courses, only the route definition is touched. The complex business logic, validation algorithms, and database transactions in the controller remain completely unaffected and isolated.

2. Why Middleware Exists

Middleware functions act as security guards and pre-processors. Instead of duplicating JWT verification or file-size checks inside every single controller, middleware executes first. If the incoming token is expired or the file is not an allowed PDF/ZIP, the middleware halts the request immediately with an HTTP 401 or 400 before heavy database queries run.

3. Why the Prisma Schema is Separate from Code

Prisma uses a declarative modeling syntax in schema.prisma instead of inline JavaScript models. This acts as the single source of truth for the entire database. Running prisma migrate translates this schema into immutable SQL migration files, while prisma generate builds the strongly-typed JavaScript query builder used by controllers.

3.2 Key Technology Relationships Explained

1. Prisma ORM vs PostgreSQL: Who Does What?

A common beginner confusion is thinking Prisma is the database. It is not. PostgreSQL is the database server hosted on Neon that physically stores your tables, records, and indexes on disk. Prisma is an Object-Relational Mapper (ORM) that lives inside your Express server code.

When your controller executes prisma.user.findUnique({ where: { email } }), Prisma's Rust query engine constructs a parameterized SQL query: SELECT id, name, email, password, role FROM "User" WHERE email = $1 LIMIT 1. It sends this query over TCP to PostgreSQL, parses the database response rows, and returns a clean JavaScript object.

2. Vercel vs Render vs Neon: Why Three Different Clouds?

CampusHub uses modern specialized cloud hosting rather than a monolithic virtual private server:

  • Vercel (Frontend): Serves static assets across global edge locations. When a user in Delhi or New York visits the site, the HTML, JS, and CSS load from the nearest edge server in milliseconds.
  • Render (Backend): Runs a continuous Node.js server that listens for incoming API traffic, verifies authentication, and computes business logic.
  • Neon (Database): Runs serverless PostgreSQL in AWS us-east-2. Neon automatically scales compute, handles automated backups, and provides connection pooling for high-concurrency queries.
EXECUTION PIPELINES

Part 4 — Request Lifecycle & Core Application Workflows

4.1 The Standard 10-Step HTTP Request Lifecycle

Every dynamic interaction in CampusHub follows an orchestrated ten-step pipeline between browser, network, middleware, business controllers, and PostgreSQL:

  1. User Action: User interacts with a React UI component (e.g., submitting registration or a quiz answer).
  2. Client-Side Validation: Component performs instant checks (email format, password length, required fields) to eliminate invalid network calls.
  3. HTTP Client Dispatch: Centralized api() helper increments the active request counter (triggering the top loading bar), retrieves JWT from localStorage, injects Authorization: Bearer <token>, and dispatches the fetch call.
  4. Network Ingress: Request traverses TLS 1.3 across the internet to the Express 5 server hosted on Render.
  5. Global Middleware: Express invokes cors() and express.json({ limit: "5mb" }) to parse incoming payload buffers into req.body.
  6. Route & Security Guards: Route-specific middleware executes: authenticate verifies the JWT signature; authorizeStudent or authorizeTeacher verifies role permissions.
  7. Controller Business Validation: Controller evaluates domain rules (deadline expirations, course enrollments, duplicate checks).
  8. Prisma ORM & PostgreSQL: Controller executes type-safe queries or atomic prisma.$transaction blocks.
  9. Structured HTTP Response: Controller returns an explicit HTTP status (200, 201, 400, 403, 409) with JSON payload: { success, message, data }.
  10. State Reconciliation: api() decrements the loading counter; React updates state, re-renders the DOM, or triggers navigation.

4.2 Individual Workflow Traces

Flow A: Direct Registration Lifecycle

Frontend: SignupPage.jsx | Backend Route: POST /api/auth/register | Controller: auth.controller.js

Registration is completely streamlined: User submits name, email, and password. The controller normalizes email to lowercase, checks for duplicates via prisma.user.findUnique (returning HTTP 409 if taken), hashes the password with bcrypt.hash(password, 10), and inserts the user directly into PostgreSQL with role STUDENT. Upon receiving HTTP 201, the frontend redirects directly to /login, pre-populating the email field with a green success notification.

Flow B: Quiz Attempt & Automated Grading Pipeline

Frontend: QuizzesPage.jsx, QuizAttemptPage.jsx, QuizResultPage.jsx | Controller: quiz.controller.js

1. Attempt Initialization: When a student starts a quiz, the server verifies enrollment and availability windows. Crucially, the server strips correctAnswer and explanation from the question JSON returned to the client, preventing any client-side inspection cheats.

2. Atomic Submission & Grading: When submitted, the controller fetches the master questions, compares the student's selections, calculates the final score and percentage, and executes an atomic prisma.$transaction: marks the attempt SUBMITTED, deletes any orphan in-progress attempts, and persists all answers. The student is then redirected to the comprehensive Rubric Result page.

Flow C: Cloudflare R2 Secure Object Storage

Frontend: PrivateUploadsPage.jsx | Controller: privateFile.controller.js | Config: r2.js

1. Ingestion: Multer buffers incoming files in memory with a 25MB limit and strict MIME whitelist. The controller generates a collision-free UUID storage key: private/<userId>/<UUID>.<ext>, streams it to Cloudflare R2 via PutObjectCommand, and records file metadata in PostgreSQL.

2. Compensation Rollback: If the database write fails after the file reaches R2, a catch block automatically executes DeleteObjectCommand on R2 to prevent orphaned storage leaks.

3. Presigned Downloads: Downloads request a temporary signed URL via getSignedUrl(r2, command, { expiresIn: 60 }). The link is valid for exactly 60 seconds, ensuring files remain completely private and inaccessible without authentication.

5.4 Safe Migration Workflows & Serverless Discipline

Development: `prisma migrate dev`

In local development, developers run npx prisma migrate dev. This command compares schema.prisma against the current database state, generates a readable migration.sql script, applies it locally, and updates the local Prisma client types.

Production CI/CD: `prisma migrate deploy`

In production (Render build lifecycle), only npx prisma migrate deploy is executed. It compares committed migration files against the _prisma_migrations tracking table and applies new migrations non-interactively without prompting or modifying schema files.

Engineering Rule: Never Run `prisma db push` in Production
prisma db push synchronizes the database directly from schema files without producing migration history. In production, this can accidentally drop tables, lose historical audit trails, and break deterministic rollbacks. Production systems must always maintain an immutable, sequential migration history.
SECURITY & IDENTITY POST-MORTEM

Part 6 — Authentication System & Email OTP Removal Post-Mortem

6.1 Executive Post-Mortem: Why Email OTP Was Completely Removed

In modern full-stack development, knowing what code to delete is as critical as knowing what to write. CampusHub initially included a 6-digit email One-Time Password (OTP) verification system buffered in a PendingRegistration PostgreSQL table. During systematic staging audits, this architecture proved to be an operational bottleneck.

1. SMTP Deliverability Fragility

External transactional SMTP relays introduce unpredictable 10 to 120-second latencies and frequent spam folder false positives, leading to student drop-offs and frustrating verification loops.

2. Database State Bloat

Unverified registrations accumulated abandoned records in the database, necessitating recurring cleanup cron jobs and wasting storage on phantom accounts.

3. Frontend State Complexity

Managing cooldown timers, resend intervals, expiration countdowns, and multi-box input synchronizations added substantial frontend debt for minimal security gain.

4. The Direct Registration Solution

Replacing OTP with direct atomic registration (Register → Bcrypt → Postgres → Immediate Login) eliminated external failure points while maintaining strict cryptographic password hashing.

6.3 Current Active Trust Boundaries & Password Cryptography

CampusHub relies on industry-standard cryptographic primitives to safeguard user identities:

  • Bcrypt Salt Hashing: User passwords are never stored in plaintext. They are salted and hashed using bcryptjs with 10 salt rounds before touching PostgreSQL.
  • Constant-Time Password Comparison: During login, bcrypt.compare() prevents timing attacks by verifying password hashes in constant time.
  • Cryptographic JWT Signing: Successful logins issue an HMAC-SHA256 signed JSON Web Token carrying { id, email, role }, signed with a 256-bit environment secret (JWT_SECRET).
  • Server-Side Role Guard: All incoming requests pass through authenticateToken and authorizeRoles middleware. Tampering with the client-side role in localStorage is rejected at the API layer because the token signature verification fails.

6.4 Institutional Single Sign-On (SSO) Roadmap

For an enterprise production deployment across a university with tens of thousands of users, the recommended progression is Federated Single Sign-On:

OpenID Connect / Google Workspace

Allows students to authenticate using their official institutional email (@university.edu) via Google or Microsoft Azure AD OAuth 2.0 endpoints, eliminating password management entirely.

SAML 2.0 / Shibboleth Federation

The gold standard in higher education. Connects directly to campus identity providers (IdPs), providing centralized multi-factor authentication (MFA) and automated roster synchronization.

SYSTEMS DEBUGGING

Part 7 — 6 Real-World Debugging Case Studies

True senior engineering competence is forged during debugging. The following six case studies document real architectural challenges encountered, investigated, and permanently resolved during the development of CampusHub LMS.

CASE STUDY 1

The Invisible Modal Bug (Prop Name Mismatch)

Observable Symptom: Clicking "Create Quiz", "Add Question", or "Quiz Settings" on /teacher/quizzes triggered state updates, but the modal dialog never appeared on screen. No console errors were generated.

Root Cause: Modal.jsx expected isOpen, but the calling parent page passed open={isCreateOpen}. Because isOpen was undefined, the modal silently rendered null.

The Engineering Fix
Updated Modal.jsx with a defensive fallback: const isVisible = isOpen !== undefined ? isOpen : open; if (!isVisible) return null;. This resolved all modal invocations across the portal instantly.
CASE STUDY 2

The Race Condition Double-Attempt Bug in React 18 StrictMode

Observable Symptom: Starting a quiz generated two duplicate QuizAttempt records in PostgreSQL timestamped 1 to 3ms apart, leaving students stuck in an invalid state.

Root Cause: React 18 StrictMode double-mounts components in development. Two concurrent POST /api/quizzes/:id/start requests executed simultaneously before either had written to PostgreSQL.

The Engineering Fix
Implemented a three-layer defense: (1) Added initiatingRef = useRef(false) on the frontend to block multi-execution, (2) Made the backend start endpoint idempotent by returning existing in-progress attempts, and (3) Added an atomic transaction cleaning up zero-answer orphaned attempts.
CASE STUDY 3

Prisma 6 vs Prisma 7 VS Code Extension Conflict

Observable Symptom: VS Code editor highlighted url = env("DATABASE_URL") with errors stating url is no longer supported in Prisma 7, even though the project installed Prisma 6.19.3.

Root Cause: VS Code's Prisma extension auto-updated to v31.13.0+, running the Prisma 7 Language Server which enforced unreleased Prisma 7 configuration rules on a Prisma 6 project.

The Engineering Fix
Added "prisma.pinToPrisma6": true in .vscode/settings.json, forcing the editor language server to respect Prisma 6 syntax rules.
CASE STUDY 4

Shell Environment Sourcing Failures with Whitespace in .env

Observable Symptom: Express server defaulted to fallback ports or failed to connect to Neon database because environment variables evaluated to undefined.

Root Cause: Spaces around the equals sign (PORT = 2000) violated POSIX shell key-value parsing, causing dotenv to misidentify variable names.

The Engineering Fix
Sanitized all environment variable declarations to strict POSIX KEY=VALUE syntax with zero whitespace surrounding the equals operator.
CASE STUDY 5

S3/R2 Blob Orphan Prevention via Compensating Transactions

Observable Symptom: When database writes failed after an S3/R2 upload, binary objects remained stranded in Cloudflare R2 indefinitely with no database reference.

Root Cause: Distributed two-phase write across independent cloud services without automated compensation logic.

The Engineering Fix
Implemented the Compensating Transaction Pattern (Saga): if PostgreSQL metadata creation throws any error, the controller immediately executes DeleteObjectCommand to delete the R2 object before returning a 500 status.
CASE STUDY 6

Vercel Stale Deployment Due to Uncommitted Git State

Observable Symptom: Production URL on Vercel displayed outdated UI components and called deprecated endpoints after code edits were supposedly completed.

Root Cause: Frontend modifications were left unstaged in the local git repository; only backend commits had been pushed to GitHub.

The Engineering Fix
Standardized release checklist: run git status across both directories, stage frontend and backend changes cohesively, push to GitHub, and verify Vercel build status dashboard.

REFERENCE & INDEX

Part 13 — Technical Glossary & Project File Index

13.1 Technical Glossary (35+ Essential Industry Concepts)

Key engineering definitions contextualized within the CampusHub LMS architecture.

Atomic Transaction

A database operation wrapped in prisma.$transaction where all sub-operations succeed together or roll back completely on error, preventing partial corruption.

Bcrypt & Salt Rounds

One-way cryptographic hash with 10 salt rounds (1024 work factor) protecting user passwords against rainbow tables and brute-force cracking.

Compensating Transaction (Saga)

An explicit undo operation (deleting an uploaded R2 file) triggered when a subsequent distributed database insert fails.

Connection Pooling (PgBouncer)

Neon's managed proxy caching physical PostgreSQL connections, enabling instant query execution across ephemeral serverless requests.

Presigned URLs (60s TTL)

Cryptographically signed URLs allowing authorized clients direct download access to Cloudflare R2 objects without making the bucket public.

Idempotency

Designing API endpoints so that repeated identical requests produce the same side-effect as a single request (e.g., starting an active quiz session).
